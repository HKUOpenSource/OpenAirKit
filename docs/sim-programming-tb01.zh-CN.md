# TB01 实验 SIM 烧录方法

[English](sim-programming-tb01.md)

## 在端到端搭建中的快速定位

在将物理 SIM 卡插入 Jetson UE 之前（参见[端到端快速搭建指南](quickstart.zh-CN.md)）：

1. 在 Open5GS 中为**每台 UE 创建独立订阅**（`stacks/open5gs/subscriber.py`），使用各自独立的
   **IMSI**、**Ki** 与 **OPc**，`sqn=0`、单 IPv4 PDU、`dnn=oai`、`sst=1`、`five_qi=9`
   （需与[UE 接入与实验室策略](ue-access-policy.zh-CN.md)对齐）。
2. 将导出的 `sim.json` 与订阅密钥存放在 Git 之外的私密目录中（目录 `0700`、文件 `0600`）。
3. 按下文经核验的 `GRSIMWrite 4.4.9+` 协议细节烧录 TB01 白卡（PC/SC 显式 `T=0`、精确
   TB01 ATR、**Milenage 选择值 `00`**），并核对 IMSI 读回与本地 AUTS MAC-S 一致后再上卡测试。

## 背景与适用范围

本文记录 2026-10-16 在本机完成的一次实际烧录，以及过程中发现并修正的问题。
适用范围是已核对的 GRSIMWrite 4.4.9+ 软件和本次 TB01 卡片，不代表其他
TB01 固件或其他型号也兼容。烧录适配器保存在本机私密工作目录中，尚未作为
仓库发布工具集成。

## 工具与卡片识别

- 本机使用 Python 3.12 私有虚拟环境、`pyscard 2.3.1` 和官方 Osmocom pySim，
  pySim 固定在提交 `9aa8934da2415b161eb9726adad2ba7b4f35d1a7`。
- 读卡器使用系统 PC/SC；连接从首次 `connect` 就显式指定 **T=0**，
  不先自动协商 T=0 / T=1，也不回退到 T=1。
- 本次精确匹配的 ATR 为 `3B9E94801FC78031E073FE211366425454423031DB`。
  该匹配用于识别商家软件中的 TB01 分支，不能证明卡片的零售型号或全部 COS 能力。
- 商家 EXE / DLL 只做离线分析，没有在本机或 Wine 中执行。
  已核对的 `GRSIMWrite.exe` SHA-256 为
  `ed4912990f5a2bd5dcbf38df9743d3028a842d2b7ac5594b9825c0627eb48fe5`。

## SADM 与 ADM 的关系

TB01 的厂商检查流程使用软件内置的 **SADM**：将 16 个十六进制字符解码成
8 个原始字节，再放入厂商专用 APDU。它与软件界面中的 ADM 字段、修改 ADM
的命令分别处理，不能据此认定 SADM 就是标准 ADM1。

本次在单独授权的管理权限检查阶段，SADM 检查返回 `9000`，当时没有写卡。
后续烧录任务在新的操作记录中执行了所需的 SADM 检查。每个任务均记录执行状态，
不自动重试。`9000` 只证明该厂商检查被接受；具体写入权限仍由后续每条命令的
结果确认，不能推断所有文件都可写。

SADM、软件默认 ADM 和厂商命令中的固定前缀均不在本文公开，不通过猜测 ADM
获取权限。它们的实际值只在受限的本机流程中使用。

## 本次烧录顺序

1. **先核对核心网资料。** 在 Spark 上用只读脚本比较私密 SIM 文件与当前运行的
   Open5GS 唯一对应订阅，检查 IMSI、Ki、OPc、AMF、OPc 模式、订阅启用状态及
   预期 DNN / SST。脚本仅导出脱敏比较结果，没有重建订阅、重置 SQN 或重启服务。
2. **私密传输资料。** 通过 SSH / SCP 将原有 `sim.json`、`identity.json` 和比较结果
   传到本机受限目录，并核对文件一致性。目录权限为 `0700`，文件为 `0600`。
   不重新生成密钥；输入是 OPc 时，不再把它当 OP 重算 OPc。
3. **只读预检和备份。** 要求恰好一个读卡器、独占 T=0 连接和完整 ATR 精确匹配；
   从 MF / EF.DIR 找到唯一 USIM 应用。私密备份 ICCID、USIM IMSI、EF.AD，
   核对文件长度和目标 MNC 长度；没有读取 Ki / OPc。写入前再次确认仍是原卡。
4. **验证后先写 IMSI。** 选择 MF，执行厂商 SADM 检查；选择 ADF.USIM 下的
   EF.IMSI（`6F07`），用 pySim 的 `enc_imsi` 编码成 9 字节，再执行 UPDATE BINARY，
   立即读回比较。若文件访问被拒绝，必须在写 Ki / OPc 前停止，不尝试其他 ADM。
5. **写 USIM 鉴权资料。** 回到 MF，按已分析的 TB01 模板写入 Ki、OPc 和算法选择。
   不执行格式化、擦除、EF.DIR 重建、GSM / CDMA 分支或 PIN / PUK / ADM 修改。
   如需调整 EF.AD，只修改第 4 字节的 MNC 长度低半字节并保留其他位；本次无需调整。
6. **重新连接并验证。** 确认 IMSI 持久化、ICCID 保留、MNC 长度正确。用目标
   Ki / OPc、本地随机 RAND 和 AMF 构造一个 USIM 3G AKA 验证向量；本次使用与
   核心网核对结果一致的初始 SQN 0，不修改核心网 SQN。
7. **修正算法选择并复验。** 首次验证暴露算法选择错误，按下文修正为 `00`。
   修正只发送 SADM 检查、算法设置和一次 AKA；没有重写 IMSI、Ki 或 OPc。
   最后校验有效 AUTS，保存脱敏完成报告并关闭读卡器连接。

## TB01 命令布局与编码要点

以下是本次核对的布局说明，尖括号表示私密数据，不能直接作为可执行指令使用。
厂商固定前缀从已核对二进制中私密提取；其含义未独立确认，不将它解释成标准 ADM。

| 操作 | 布局 |
| --- | --- |
| 厂商 SADM 检查 | `00 FB FF FF 08 <SADM:8 bytes>` |
| USIM IMSI | 在正确 USIM 文件上下文中：`00 D6 00 00 09 <encoded IMSI:9 bytes>` |
| USIM Ki | `00 FB 00 00 18 <fixed prefix:8 bytes> <Ki:16 bytes>` |
| USIM OPc | `00 FB 00 10 19 <fixed prefix:8 bytes> 01 <OPc:16 bytes>` |
| USIM Milenage | `00 FB 00 00 09 <fixed prefix:8 bytes> 00` |

不同命令的固定前缀分别保留原值，不能互换。OPc 命令中的 `01` 是该模板的
固定字段，不是算法选择值。Ki 和 OPc 均由 32 个十六进制字符解码成 16 字节；
AMF 是 2 字节。IMSI 使用标准编码函数，不把数字字符串直接当作 APDU 数据。

## 算法选择错误及修正依据

首次实现把 Delphi 字段记录中“名称后面的 DWORD”误认为当前控件偏移；
实际当前记录的偏移位于名称前 7 字节，原读取位置属于下一条记录，导致
Milenage / XOR 控件映射颠倒。首次 IMSI、Ki、OPc 写入均返回 `9000`，但错误的
算法值 `01` 使 AUTHENTICATE 返回 `9862`（MAC 不正确）。这不是 SQN 同步失败。

重新核对字段记录、界面数据和命令构造分支后，确认：

- `RadLTE_MLG` 控件偏移为 `0x614`，`RadLTE_XOR` 为 `0x618`。
- 软件检查 XOR 控件并映射为内部枚举 9；TB01 构造器将枚举 9 编码为 `01`，
  其他分支编码为 `00`。
- 因此本次 TB01 的 **Milenage = `00`，XOR = `01`**。

修正版通过 13 项离线测试，包括错误字段记录拒绝、仅修正算法时禁止重写 IMSI /
密钥，以及 Milenage 标准向量检查。原始操作与修正记录都保留在私密目录中。

## 响应处理与防止重复操作

- `61xx` 表示有待取回的数据，按长度执行有界 GET RESPONSE。本次最终验证先收到
  `6110`，取回数据后为 `9000`，内容是 `DC 0E` 开头的 AUTS。
- AUTS 的 MAC-S 使用同一 Ki / OPc、恢复的卡片 SQN 和同步流程的 `AMF=0000`
  校验。验证通过说明密钥匹配；后续仍需实际入网验证网络接受同步并成功注册。
- 对鉴权或写入指令不自动重试，包括收到 `6Cxx` 时；若出现 `63Cx` 等重试计数
  提示、超时或状态不明，停止并保留现场，不试其他管理码。
- 每次鉴权和修改前先将操作写入持久日志并同步落盘，限制命令、次数及文件上下文。
  只读工具与写入适配器分离。已完成日志阻止重复烧录；不得删除日志来绕过保护。
