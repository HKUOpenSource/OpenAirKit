# 与原 Biverge 的切换设计

## 1. 可实现的目标

新旧配置、数据和网络独立；B210 是唯一必须串行交接的硬件。安装新栈兼容单元并通过验收后，切回仍使用服务器上的原命令：

```sh
~/.local/bin/oai-spark-services.sh start
```

不修改或替换此脚本，不修改 Biverge 仓库。切回纯 OAI 的含义是旧 gNB + 旧核心网承载 UE 业务，新栈服务停止，但保留新数据卷和网络供下次使用。

当前仓库只包含设计和模板；以上不是已经部署完成的保证。原脚本或服务名以后变化时必须重新验收这一契约。

## 2. systemd 交接机制

原脚本按序启动旧核心网、采集器、Web、iperf3 及健康定时器，最后启动 `oai-gnb.service`。新 `aoc-stack.target` 和 `aoc-gnb.service` 均声明 `Conflicts=oai-gnb.service`；新 gNB 同时声明 `After=oai-gnb.service`。所有新子服务声明 `PartOf=aoc-stack.target`。

`Conflicts` 的停止行为是双向的；配合显式排序，切换时先停止对方再启动本方。`PartOf` 将停止新 target 的动作传播到新核心网与监控。依据：[systemd 官方 unit 语义](https://github.com/systemd/systemd/blob/v255/man/systemd.unit.xml)。不需要往旧 unit 写 drop-in，但新单元必须先安装并 daemon-reload。

```text
旧 -> 新：先完成静态/实时检查与新核心网健康预检
         启动 aoc-stack.target
         -> 停旧 oai-gnb -> 释放 B210 -> 启动 OCUDU -> 验证新 N2/UE

新 -> 旧：执行原脚本 start
         -> 原脚本启动 oai-gnb
         -> systemd 停新 target 及其子服务
         -> 等待新 gNB 完全退出 -> 旧 gNB 打开 B210
         -> 原脚本继续原有稳定性/平台检查 -> 验证旧 UE 业务
```

新栈运行期间可保留原核心网和原监控，便于快速切回；它们不承载新的 UE 链路，也不作为新栈的数据源。切回时新核心网/监控的停止由 target 传播；N2 与 B210 的交接由两个 gNB 的显式排序保证。

## 3. 约束与失败处理

- 所有射频启动必须通过这两个受管理 unit；直接从 shell 启动 gNB 会绕过 systemd 契约。新 `radio-preflight` 应拒绝未知占用，不能使用 `pkill` 清理其他进程。
- 不使用 `mask`、修改旧服务 enable 状态、关闭 Docker daemon 或移除旧网络来实现切换。新栈默认不开机自启，不配置后台定时器反复拉起 gNB。
- 原脚本已有自己的 flock；本项目未来切换 CLI 应参与同一用户、同一 runtime 目录的锁，且通过锁文件 inode 与原脚本一致性测试。不能假设另建一个锁就覆盖旧脚本。直接 systemctl 并发请求可能被取消/失败，但不应形成双 RAN 占用。
- 先构建和预检新核心网，再进入射频窗口。新栈切换失败时记录状态并停止新 target，再执行原脚本恢复。模板本身不提供自动回滚事务；未来 CLI 必须实现失败清理，禁止失败后无限争抢设备。
- systemd active 不是无线验收。必须确认旧进程完全退出、B210 释放、新 N2 对端正确、UE 重注册及 PDU 地址属于预期地址池。
- 若停止超时或设备仍占用，应终止切换并报告；不得自动 USB reset 或覆盖共享 UHD。清理策略需在实际 wrapper 中实现和测试。

## 4. 已发现的旧栈前提

现场旧 `oai-ext-dn-iperf3.service` 已存在监督脚本引号错误和持续重启问题。原启动脚本在 gNB 之前启动该服务，并在之后要求它保持 active，因此可能在触发切换前退出，也可能导致最终健康检查失败。这是原环境已有问题；本仓库不修改该脚本，也不把问题掩盖为“切换成功”。

在认定“原脚本一键切回”达到验收标准前，需要在原项目中解决或确认该故障的当前状态。详见[原环境调研](research/project-research-2026-09-07.zh-CN.md)。

## 5. 验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| OAI 正常运行时切新栈 | 旧 gNB 完全退出，新 gNB 才打开 B210；旧核心网/平台不被破坏 |
| 新栈正常运行时执行原脚本 | 新 target 和服务退出；原脚本完成，新旧数据卷均保留 |
| 新核心网启动失败 | 射频窗口前被预检拦截，旧链路继续服务 |
| 新 gNB 启动失败/超时 | 停止新 target 后可用原脚本恢复；不残留 USB 持有者 |
| 连续往返至少 5 次 | 无地址/端口泄漏、孤儿进程、自动重启争用或认证 SQN 故障 |
| 两个入口并发执行 | 单一设备持有者；失败命令返回明确状态 |
| UE 业务回归 | 重新注册、PDU 建立、预期 IP、双向连通、吞吐及恢复成功 |

先在隔离 Linux/systemd 环境用不接触 B210 的替身服务验证依赖图、启动失败和停止超时，再安排 Spark 射频窗口。当前只执行过本地配置校验，未执行此矩阵。
