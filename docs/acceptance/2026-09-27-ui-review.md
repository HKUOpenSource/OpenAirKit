## Product and framework constraints

Each Jetson Console manages its own device and state. Fleet inventory, global
device context and mandatory device-identification UI are outside this work.
Spark continues to show only the RAN, core and UE evidence available at its own
base station. These boundaries apply even if the deployment grows substantially.

**Keep Astryx.** Retain `@astryxdesign/core`, `@astryxdesign/charts`, Neutral theme
and the existing `UIProvider`. Reuse Astryx navigation, controls, tables, dialogs,
banners, charts and layout primitives; use theme tokens and the existing shared
layout layer. Do not introduce another component library or replace Astryx
components with a parallel visual system. Runtime copy remains English.

## Method and observations

Question: which current UI behaviors obstruct understanding local state,
identifying a fault or completing an operation, and what should change first?
No CodeGraph index exists. Source inspection covered both frontends, their data
contracts, shared styles and browser tests. Browser checks used current built
assets, a local Jetson simulator and synthetic Spark observations through the
real local backend. No production device was operated on.

Desktop checks used 1280 × 720; mobile checks used 390 × 844. The Spark fixture
contains two synthetic subscribers and incomplete hardware/runtime evidence;
its warnings are expected fixture behavior, not a claim about the live Spark.
Ignored screenshots and the disposable harness are under
`local/ui-review-20260927/`. No production identities or screenshots were used.

The existing restrained Astryx appearance, page shells, skip link, labeled
controls and evidence-quality model are useful foundations. The main work is
correctness, information hierarchy and feedback rather than a new visual theme.

## Prioritized findings

### 1. P1 — Device state filters do not match their evidence semantics

**Source and browser evidence.** Selecting Connected in Spark produced zero
results despite two registered synthetic subscribers. This result is consistent
with the source: `freshDevice` intentionally limits subscriber connection state
to registered/disconnected/unknown, but Devices still offers Connected. Separately,
Active checks fresh session `status=ok` without checking `session.state`; it can
include inactive/unknown PDU reports. The resulting empty message says “No device
evidence”, even when evidence exists but does not match the filter.

Paths: [freshness.ts](../../apps/spark-platform/frontend/src/freshness.ts), lines
19–28; [DevicesPage.tsx](../../apps/spark-platform/frontend/src/pages/DevicesPage.tsx),
lines 78–86; [OverviewPage.tsx](../../apps/spark-platform/frontend/src/pages/OverviewPage.tsx),
lines 98–104. Use explicit registration, PDU and freshness filters with Astryx
Selector. Share the Active predicate, and distinguish no matching results from
no data. Do not manufacture end-to-end Connected state from Spark evidence.
Validate active/inactive/unknown/expired sessions and empty filtered results.

### 2. P1 — Operation failures can be hidden or disappear before the user responds

**Confirmed source behavior; failure submission was not browser-tested.** Jetson
keeps its confirmation dialog open on failure but writes the error to a background
Banner. A recover task can be created successfully before its run request fails;
Confirm then repeats creation rather than identifying the existing task. Spark
also renders submission errors outside its dialog, and successful task polling
clears the shared error every one/five seconds. Several Jetson job/maintenance
actions and Spark cancellation lack a pending state.

Paths: Jetson [main.tsx](../../apps/jetson-console/frontend/src/main.tsx), lines
159–176 and 343–374; [components.tsx](../../apps/jetson-console/frontend/src/components.tsx),
lines 169–190; Spark [SecondaryPages.tsx](../../apps/spark-platform/frontend/src/pages/SecondaryPages.tsx),
lines 418–466 and 519–531. Keep errors inside the Astryx dialog, separate request
errors from operation outcomes, retain the created task ID, and disable competing
actions while requests are pending. Test delayed responses, create-success/run-failure,
submit/cancel failures and continued polling while an error is displayed.

### 3. P2 — History is incomplete and can misrepresent freshness or time range

**Source evidence.** Jetson History and Recent activity refresh mainly when
`jobs.length` changes. New events or task progress need not change that count.
History ignores the backend's `next_cursor`, leaving records beyond the first 100
unreachable. Selecting 30 days silently caps metric queries to seven days; chart
axes show only hours/minutes and the last valid value lacks its timestamp. Rapid
filter changes have no request cancellation or result-order guard. Spark History
can select only entities/metrics still present in the current snapshot.

Paths: Jetson [pages.tsx](../../apps/jetson-console/frontend/src/pages.tsx), lines
85–92 and 540–556; [components.tsx](../../apps/jetson-console/frontend/src/components.tsx),
lines 110–138; [store.py](../../apps/jetson-console/backend/aoc_jetson/store.py),
lines 97–102; Spark [SecondaryPages.tsx](../../apps/spark-platform/frontend/src/pages/SecondaryPages.tsx),
lines 157–163. Add independent refresh, cursor loading, actual range labels,
last-sample time and ordered requests. Keep offline historical entities selectable
within Spark's retained local evidence. Test >100 records, unchanged task counts,
out-of-order responses, seven/30-day ranges and offline entities.

### 4. P2 — Event-type choices disappear after filtering

**Browser reproduced.** The initial options were All types, Device Change and
Radio State. After choosing Device Change and reopening the selector, only All
types and Device Change remained. `kinds` is derived from the already filtered
results at [EventsPage.tsx](../../apps/spark-platform/frontend/src/pages/EventsPage.tsx),
lines 50–52 and 151–160. Supply stable facets or a supported event-type catalogue.
Test direct A→B switching, empty results and types absent from the first page.

### 5. P2 — gNB information hierarchy and history loading need consolidation

**Visual and source evidence.** The page renders eight equally weighted summary
cards, runtime/RF details and 15 full trend panels before Radio contexts. In the
1280 × 720 fixture, Radio contexts began around y=3740; this is a measured example,
not a fixed layout invariant. At 390 × 844, CPU utilization, used cores and host
CPU share occupy the first three summary cards, ahead of N2 and traffic.

Each Trend independently requests all historical metrics for the same entity/time
window, with slightly differing `since` values, then filters locally. This creates
15 overlapping requests per refresh cycle rather than a shared history result.
Paths: [GnbPage.tsx](../../apps/spark-platform/frontend/src/pages/GnbPage.tsx),
lines 86–105 and 198–237; [components.tsx](../../apps/spark-platform/frontend/src/components.tsx),
lines 499–526. Put radio health/N2/traffic/contexts first; group signal, scheduling
and host-resource charts; progressively reveal runtime/configuration details.
Use Astryx layout and Charts with one shared entity/window history request.
Validate useful first-screen content and request counts, not only lack of overflow.

### 6. P2 — Setup compares raw values without explaining the decision

**Visual and source evidence.** The table mixes exact targets, observed-only
values, an address pool and values the UE cannot report. Users must infer which
differences matter and what the plan would change. On a 390-pixel viewport the
600-pixel table places Target outside the initial visible area. Horizontal scrolling
works; the issue is simultaneous comparison, not page overflow.

Path: [pages.tsx](../../apps/jetson-console/frontend/src/pages.tsx), lines 434–534.
Add Matched / Different / Observation only / Unknown meanings, unmet prerequisites
and a concrete change summary. Keep the Astryx Table on desktop and use stacked
Astryx rows/cards on narrow screens so current/target/result stay together.
Test mismatches, unreported observations, valid in-pool addresses and blocked plans.

### 7. P2 — Navigation hides operational tools in Account

**Browser confirmed.** Spark's Account menu contains Operations, Diagnostics and
Metric history alongside Sign out; these pages have no selected primary-nav item.
Path: [main.tsx](../../apps/spark-platform/frontend/src/main.tsx), lines 316–338.
Use a clearly labeled tools/operations group in Astryx navigation. Add contextual
links from a fault or event to relevant history/diagnostics; carry entity and time
context. Keep account actions in Account. This remains single-station navigation.

### 8. P2 — State and time wording is inconsistent across pages

**Browser and source evidence.** Spark's green “Available” reports collector/data
availability while a yellow operational warning can be shown concurrently. The
gNB banner exposes `radio_evidence_unavailable` and an ISO timestamp with fractional
seconds, while Overview uses a formatted local time. A first unauthenticated visit
also displayed “Session expired” because the initial session probe dispatches the
same event as a genuinely expired session.

Paths: [page-ui.tsx](../../apps/spark-platform/frontend/src/page-ui.tsx), lines
25–47; [GnbPage.tsx](../../apps/spark-platform/frontend/src/pages/GnbPage.tsx),
lines 75–84; [api.ts](../../apps/spark-platform/frontend/src/api.ts), lines 9–10;
[main.tsx](../../apps/spark-platform/frontend/src/main.tsx), lines 109–137.
Use clear evidence labels such as “Live data” and “Evidence stale”, readable
operational explanations and one time formatter. Preserve the distinction between
observation quality and business health. Separate first sign-in, reconnecting,
initial-load failure and session expiration, with explicit retry where useful.

## Implementation sequence and acceptance

1. Correct status predicates, operation feedback and stable filters first.
2. Reorganize Overview/gNB/Setup around local status, fault cause and next action;
   update navigation and history behavior using Astryx.
3. Refine spacing, typography and mobile composition within the Neutral theme;
   consolidate history requests and measure rendering before further optimization.

Retain existing data-quality and chart-gap protections. Add desktop/mobile and
intermediate-width checks (390/768/1024/1280), keyboard-only navigation, dialog
focus/return, 200% zoom, long errors, delayed requests, stale evidence, no matches,
and interrupted operations. Existing tests mostly cover 1440/390 widths and happy
paths; their presence is not evidence these additional scenarios passed.

The browser's automatic approval review rejected clicking “Create setup plan” in
the simulator because it might create persistent operational task state. No
alternative write path was used; operation failure/dialog conclusions above use
source evidence. No mutation workflow, keyboard/zoom matrix, performance profile
or production hardware acceptance was executed. Local preview services were
stopped after inspection. Paired documentation and link/whitespace audits cover
the report edits; the previously completed code checks were not rerun for this
documentation-only review.
