## 产品与框架约束

每台 Jetson Console 只管理自身设备和状态。全局设备清单、跨设备上下文和强制设备
身份展示不属于本轮范围。Spark 继续展示自身基站可获得的 RAN、核心网与 UE 证据。
即使接入规模增大，也保持这些职责边界。

**必须保留 Astryx。** 继续使用 `@astryxdesign/core`、`@astryxdesign/charts`、
Neutral theme 和已有 `UIProvider`。复用 Astryx 导航、控件、表格、弹窗、Banner、
图表与布局组件，通过主题 token 和现有共享布局层调整界面。不引入另一套组件库，
不建立绕过 Astryx 的平行视觉体系。运行界面继续使用英文。

## 方法与总体判断

问题：当前 UI 哪些行为妨碍用户理解本机状态、定位故障或完成操作，应先优化什么？
仓库无 CodeGraph 索引，直接检查两个前端、数据契约、共享样式和浏览器测试。
浏览器使用当前构建产物、本地 Jetson 模拟器，以及合成 Spark 数据配合真实本地后端。
没有操作生产设备。

桌面检查尺寸为 1280 × 720，手机为 390 × 844。Spark 合成数据含两个测试订阅者，
硬件/运行证据有意不完整；其告警是样例状态，不表示真实 Spark 出现同样故障。
截图与临时检查脚本保存在忽略目录 `local/ui-review-20260927/`，未使用生产身份或截图。

现有 Astryx 风格、页面框架、跳转正文入口、带标签控件和证据质量模型可以保留。
主要工作是状态正确性、信息层级和操作反馈，而不是更换主题。

## 按优先级排列的发现

### 1. P1 — 设备状态筛选与证据含义不一致

**源码与页面证据。** Spark 中两个合成订阅者已注册，选择 Connected 后结果为零。
这与源码一致：`freshDevice` 有意把订阅者连接状态限制为 registered/disconnected/
unknown，但页面仍提供 Connected。另一个问题是 Active 只检查会话 `status=ok`，
不检查 `session.state`，会将 inactive/unknown 的新鲜 PDU 报告算入 Active。
筛选无结果时文案为“No device evidence”，未区分有证据但不匹配筛选的情况。

路径：[freshness.ts](../../apps/spark-platform/frontend/src/freshness.ts) 第 19–28 行；
[DevicesPage.tsx](../../apps/spark-platform/frontend/src/pages/DevicesPage.tsx) 第 78–86 行；
[OverviewPage.tsx](../../apps/spark-platform/frontend/src/pages/OverviewPage.tsx) 第 98–104 行。
建议通过 Astryx Selector 分别表达注册、PDU 和新鲜度，共用 Active 判断，并区分
“无匹配结果”和“没有数据”。不能根据 Spark 的局部证据制造端到端 Connected。
验收应覆盖 active/inactive/unknown/expired 会话及筛选空结果。

### 2. P1 — 操作失败可能被弹窗遮挡，或在用户处理前消失

**源码行为已确认，未通过浏览器提交失败操作。** Jetson 确认失败时保持弹窗，但将
错误写到背景 Banner。Recover 可能已创建任务而运行请求失败，此时再次 Confirm
会重走创建流程，没有明确指向已有任务。Spark 同样将错误放在确认框外；后台任务
轮询成功后每隔 1/5 秒清除共用 error。Jetson 部分运行/取消/维护操作及 Spark 取消
操作还缺少请求中的状态。

路径：Jetson [main.tsx](../../apps/jetson-console/frontend/src/main.tsx) 第 159–176、
343–374 行，[components.tsx](../../apps/jetson-console/frontend/src/components.tsx)
第 169–190 行；Spark [SecondaryPages.tsx](../../apps/spark-platform/frontend/src/pages/SecondaryPages.tsx)
第 418–466、519–531 行。建议在 Astryx 弹窗内显示错误，分开读取错误和操作结果，
保留已创建任务 ID，请求中禁用竞争操作。测试慢响应、创建成功但运行失败、提交/取消
失败，以及错误展示期间继续轮询。

### 3. P2 — 历史记录不完整，新鲜度与时间范围可能被误读

**源码证据。** Jetson History 和 Recent activity 主要在 `jobs.length` 变化时刷新，
新事件和已有任务进度不一定改变这个数量。History 忽略后端 `next_cursor`，超过
前 100 条的记录没有继续查看入口。选择 30 天却静默将指标查询限制为 7 天；横轴
只有时分，最后有效值未标出时间。快速切换筛选没有取消旧请求或结果顺序保护。
Spark History 只能选择当前快照仍包含的实体/指标。

路径：Jetson [pages.tsx](../../apps/jetson-console/frontend/src/pages.tsx) 第 85–92、
540–556 行；[components.tsx](../../apps/jetson-console/frontend/src/components.tsx)
第 110–138 行；[store.py](../../apps/jetson-console/backend/aoc_jetson/store.py)
第 97–102 行；Spark [SecondaryPages.tsx](../../apps/spark-platform/frontend/src/pages/SecondaryPages.tsx)
第 157–163 行。建议增加独立刷新、游标加载、实际范围、最后样本时间与请求顺序保护。
Spark 已保留的本地历史证据应允许选择离线实体。测试超过 100 条、任务数量不变、
请求乱序、7/30 天范围，以及当前已离线的实体。

### 4. P2 — 事件类型筛选后，其他类型从选项中消失

**页面已复现。** 初始下拉框有 All types、Device Change、Radio State；选中
Device Change 后再次打开，只剩 All types 和 Device Change。原因是 `kinds`
来自已经筛选过的结果集：[EventsPage.tsx](../../apps/spark-platform/frontend/src/pages/EventsPage.tsx)
第 50–52、151–160 行。建议使用稳定的分类列表或独立分类统计接口，验证 A→B 直接
切换、空结果和目标类型不在第一页的情况。

### 5. P2 — gNB 页的信息层级和历史请求需要集中整理

**页面与源码证据。** 八张同等权重的摘要卡、运行/RF 细节和 15 个完整趋势图都排在
Radio contexts 前面。在 1280 × 720 样例中，Radio contexts 位于约 y=3740；
这是此次测量，不是固定布局常量。390 × 844 时，前三张摘要依次为 CPU 利用率、
使用核数、主机 CPU 占比，N2 和流量的优先级被压低。

每个 Trend 还独立请求同一实体/时间窗的全部历史指标，`since` 仅有细微时间差，
随后在浏览器筛选指标，每轮刷新形成 15 个重叠请求。路径：
[GnbPage.tsx](../../apps/spark-platform/frontend/src/pages/GnbPage.tsx) 第 86–105、198–237 行；
[components.tsx](../../apps/spark-platform/frontend/src/components.tsx) 第 499–526 行。
建议前置无线健康、N2、流量和上下文；按信号、调度、主机资源分组趋势图，运行/配置
细节逐步展开。保留 Astryx 布局和 Charts，历史数据按实体/时间窗统一请求。
验收不仅检查无溢出，还要检查首屏有用信息和请求数量。

### 6. P2 — Setup 只并列原始值，没有解释差异与决策

**页面与源码证据。** 表格混合严格目标、只观测项、地址池和 UE 无法报告的字段，
用户需要自行判断哪些差异重要、本次计划会修改什么。在 390 像素视口，600 像素
宽表格的 Target 列位于初始可见范围之外。横向滚动可用，问题在于难以同时比较，
而不是整个页面溢出。

路径：[pages.tsx](../../apps/jetson-console/frontend/src/pages.tsx) 第 434–534 行。
建议增加 Matched / Different / Observation only / Unknown 的含义、未满足前提
和实际变更摘要。桌面保留 Astryx Table，窄屏通过 Astryx 行/卡片布局，让当前值、
目标值和判断保持在一起。测试不匹配、无法观测、地址在范围内以及计划被阻止的状态。

### 7. P2 — 核心运维工具放在 Account 菜单，不容易发现

**页面已确认。** Spark 将 Operations、Diagnostics、Metric history 与 Sign out
放在 Account 菜单中，这些页面也没有对应主导航选中项。路径：
[main.tsx](../../apps/spark-platform/frontend/src/main.tsx) 第 316–338 行。
建议使用 Astryx 导航增加明确的工具/运维分组，并从故障或事件链接到相关历史/诊断，
携带实体和时间上下文。Account 保留账户动作，整体仍是单基站导航。

### 8. P2 — 状态和时间文案不统一，内部实现信息进入主要界面

**页面与源码证据。** 顶栏绿色 Available 表示采集/数据可用，可与黄色运行告警同时
出现，但标签没有说明层次。gNB Banner 直接显示 `radio_evidence_unavailable`
和带小数秒的 ISO 时间，Overview 又使用格式化本地时间。首次未登录访问还显示
“Session expired”，因为初始会话探测与真正过期共用事件。

路径：[page-ui.tsx](../../apps/spark-platform/frontend/src/page-ui.tsx) 第 25–47 行；
[GnbPage.tsx](../../apps/spark-platform/frontend/src/pages/GnbPage.tsx) 第 75–84 行；
[api.ts](../../apps/spark-platform/frontend/src/api.ts) 第 9–10 行；
[main.tsx](../../apps/spark-platform/frontend/src/main.tsx) 第 109–137 行。
建议使用 Live data、Evidence stale 等明确证据标签，给出可理解的故障原因，共用
时间格式化。继续区分证据质量与业务健康；首次登录、重新连接、首次加载失败和会话
过期应分别表达，必要时提供明确重试入口。

## 实施顺序与验收

1. 先修正状态判断、操作反馈和筛选稳定性。
2. 使用 Astryx 围绕本机状态、异常原因和下一步操作重排 Overview/gNB/Setup，
   同步改进导航与历史行为。
3. 在 Neutral theme 内细化间距、字体层级和移动端布局；统一历史请求，测量渲染
   性能后再做进一步优化。

保留现有数据质量和图表断点保护。补充 390/768/1024/1280 宽度、纯键盘导航、
弹窗焦点及返回、200% 缩放、长错误、慢请求、过期证据、无匹配结果和操作中断测试。
现有浏览器用例主要覆盖 1440/390 与正常流程，不能据此宣称新增场景已经通过。

浏览器自动审批拒绝点击模拟器的 Create setup plan，理由是可能创建持久化操作任务。
没有改用其他方式写入；上面的操作失败/弹窗结论采用源码证据。本轮没有执行写入
工作流、键盘/缩放矩阵、性能剖析或生产硬件验收。检查后停止本地预览服务。
报告修改执行中英文配对、链接和空白检查，文档审阅不重复运行此前已经通过的代码测试。
