# OCUDU 独立生命周期开发验证

日期：2026-09-27。源码基线：`39dde4d0216dee973ed6cbf40ecb500e83c1ac74`
及尚未提交的生命周期改动。Jetson 源码与候选包版本：0.6.0。
本记录是开发验证，不是新版本实机部署验收。

## 审阅问题与调用路径

OCUDU 能否依靠自己的流程完成安装、初始化、启动、检查和停止，而不依赖
另一项目的准备脚本或服务名称？仓库没有 `.codegraph/` 索引，审阅沿以下路径进行：

- `install-jetson.sh` → `manage.py install`：包装脚本已经选择 install，原安装文档却重复传入操作参数。
- `manage.py commission` → 已安装 Python → 硬件发现、网络前置检查与 SIM 指纹：
  系统 Python 不应导入离线模组依赖，初始化也不应停止另一控制程序。
- Jetson `platformctl.py start` → 维护助手 → `manage.py start` → 网络助手 → 设备 RPC：
  原来仅启动服务，会留下暂停观测状态，并依赖预先存在的探测路由。
- `manage.py stop` → 本项目服务 → 路由记录：设备消失后仍需清理，同时不能删除管理员路由。
- Spark `platformctl.py start/status` → 核心网健康、无线服务和 AMF gNB infoAPI：
  gNB 进程运行本身不能证明 N2 已就绪。

## 改动与影响

安装、初始化和日常运行现在各有明确命令。`commission` 替代 takeover，自动使用
已安装的应用运行环境；检查串口占用、绑定本站点 SIM 和管理设置，保持设备服务停止，
不写入模组配置。

启动检查 Wi-Fi 是首选 IPv4 默认路由，并检查到配置的 Spark 地址经 Tailscale 路由。
本站点 NetworkManager 配置仍是明确的首次部署前置条件。OCUDU 仅为配置的 UPF、
ext-DN、公网探测地址补充缺失的模组接口主机路由。复用已有正确路由但不认领；
主机路由冲突时在添加前失败。私有、原子写入的意图记录和数字协议号校验用于区分
本项目路由与结果不确定的操作。停止只删除精确匹配的自有路由，接口消失后也能清理。
归属或操作结果不确定时保留现场，要求检查。

启动会恢复设备观测，并保持自动恢复暂停。重复启动保留已经运行的观测会话。
状态分别报告服务可用性与新鲜设备连接证据。Spark 启动等待唯一 gNB 成功完成
N2 NG Setup 后才启动监测，不要求已有 UE 注册。

Jetson 校验包现在包含启动、停止和状态控制脚本。升级时应一起更新应用、匹配的
维护授权包和操作员快捷脚本。没有新增公共 API；运行时文字保持英文，安装与运维
文档提供中英文对应版本。
